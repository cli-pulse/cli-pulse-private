## #725: a cold launch with an expired access token keeps the session (all platforms)

A cold launch whose stored access token had expired signed the user out,
although the refresh token was still valid. Supabase Auth answers an expired
token on `GET /auth/v1/user` with 403 `bad_jwt`; `me()` refreshed only after a
401, and `restoreSession` deleted both tokens on any error. Access tokens live
one hour, so a relaunch more than about an hour after the last refresh hit
this, and so did a launch with no network, a timeout or a 5xx. The code has
behaved this way since the restore path was written; it is not a 1.60
regression.

- `me()` and the other `/auth/v1/user` calls refresh once on a 401, or on a
  403 whose `error_code` is `bad_jwt`, `session_not_found` or
  `user_not_found`, and retry. No other 403 is refreshed. A token whose `exp`
  has already passed is refreshed before it is sent.
- Tokens are deleted only when the refresh endpoint refuses the session (a
  JSON 4xx such as `refresh_token_not_found` or `invalid_grant`). A 5xx, 408,
  429 or non-JSON answer keeps them.
- With no answer (offline, timeout, 5xx, a failed profile read) the restore
  returns `.deferred`: the tokens stay in the Keychain, the app shows its
  sign-in screen with the existing "Server Offline" text, and the restore is
  retried after 5 s, doubling up to 1 min, until it gets an answer. Signing
  in by hand, Demo, local mode or a sign-out end the retries. The app is not
  shown as signed in until the server confirms the account.
- A refresh that a concurrent request started is joined, not discarded.
- `deleteAccount` no longer treats every refresh failure as an expired
  session.
- The Watch keeps a rotated token pair when its restore fails after a
  refresh.

Tests: `SessionRestoreExpiredTokenTests` (23 tests) plus updated guards, with
negative controls for each part of the fix (listed in #725).
